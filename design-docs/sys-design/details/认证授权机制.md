# 认证授权机制

## 1. 概述

`ai-gateway-api` 的认证授权模块位于 `model/iauth`，负责所有 OpenAPI 与 InnerAPI 的访问者身份识别与权限控制。该模块复用了 BFE 历史代码中 `users` 表同时存储“用户”与“Token”的设计，通过 `type` 字段区分两种访问者类型。

核心职责：

- **认证（Authentication）**：识别请求方是谁。支持密码登录生成 Session Key、Session Key 校验、Token 校验、调试跳过四种方式。
- **授权（Authorization）**：判断请求方能否访问某个 Feature 的某个 Action，并在需要时校验其与产品线的绑定关系。

---

## 2. 访问者模型

### 2.1 用户与 Token 共用表

`users` 表同时存储两类记录：

| `type` 值 | 含义 | 典型用途 |
|----------|------|---------|
| `0` | 普通用户 | Dashboard 管理员登录、人工操作 |
| `1` | Token | 程序化调用、Conf Agent / BFE 拉取 InnerAPI |

数据库层面的区分仅通过 `type` 字段实现；业务层分别映射为 `iauth.User` 与 `iauth.Token`。

### 2.2 `Visitor` 统一抽象

为了统一处理“用户登录”和“Token 调用”两种场景，代码中引入 `Visitor`：

```go
type Visitor struct {
    User *User
    Token *Token
}
```

`Visitor` 实现 `Loginer` 接口，统一提供 `GetName`、`GetScopes`、`GetType`、`IsAdmin` 方法。后续授权校验只关心 `Visitor`，不关心底层是用户还是 Token。

### 2.3 Scope 作用域

`Visitor.GetScopes()` 返回访问者的权限作用域列表：

| Scope | 来源 | 说明 |
|-------|------|------|
| `System` | 用户 `Admin=true` 或 Token 的 `scope="System"` | 系统管理员，拥有所有权限 |
| `Support` | Token 的 `scope="Support"` | 仅拥有导出类 Action 权限 |
| `Allowed` | 特殊值，代码中预留 | 目前未在 `scope2permission` 中使用 |

> 已移除 `Product` Scope：用户 `is_admin` 仅支持 `true`，Token `scope` 仅保留 `System`/`Support`，产品线绑定接口不再通过 OpenAPI 暴露。`user_products` 表继续保留供未来扩展。

用户是否管理员由 `users.scopes` 字段是否包含 `"System"` 决定；Token 的作用域直接取自 `users.scopes` 字段本身（创建 Token 时写入）。

## 3. 认证机制

### 3.1 四种认证方式

```go
const (
    AuthTypePassword = "Password"
    AuthTypeSessionKey = "Session"
    AuthTypeToken = "Token"
    AuthTypeSkip = "Skip"
)
```

| 方式 | 请求头示例 | 适用场景 | 是否写入 Session |
|------|-----------|---------|----------------|
| `Password` | `Authorization: Password <base64(user:pass)>` | 登录获取 Session Key | 是，生成新 Session Key 并写入 `users.ticket` |
| `Session` | `Authorization: Session <session_key>` | 常规 OpenAPI 调用 | 否，仅校验 `ticket` 是否有效、未过期 |
| `Token` | `Authorization: Token <token_value>` | 程序化调用 / InnerAPI | 否，Token 长期有效 |
| `Skip` | `Authorization: Skip System` | 调试跳过（需配置 `SkipTokenValidate=true`） | 否，生成伪造 Visitor |

> 注：实际请求头由 `endpoints/middleware/user_probe.go` 解析，格式为 `"<Type> <Identify>"`。

### 3.2 密码认证与 Session Key 生成

1. 根据用户名查询 `users` 记录；
2. 校验密码（`Extend` 字段为密码，调试时可为 `"SKIP"` 跳过校验）；
3. 循环生成 15 字节随机数，经 `base64.URLEncoding` 编码为 Session Key；
4. 确保 Session Key 不与已有记录冲突；
5. 将 Session Key 和当前时间写入 `users.ticket`、`users.ticket_created_at`。

```go
func sessionKeyFactory(len int) (string, error) {
    bs := make([]byte, len)
    _, err := rand.Read(bs)
    if err != nil {
        return "", err
    }
    return base64.URLEncoding.EncodeToString(bs), nil
}
```

### 3.3 Session Key 过期

Session Key 有效期由配置项 `RunTime.SessionExpireInDay` 决定。校验时：

```go
if user.SessionKeyCreateAt.AddDate(0, 0, stateful.DefaultConfig.RunTime.SessionExpireInDay).Before(time.Now()) {
    return nil, xerror.WrapAuthenticateFailErrorWithMsg("Session Key Expired")
}
```

### 3.4 Token 认证

Token 本质上也是 `users` 表中的一条 `type=1` 记录，其 `ticket` 字段即为 Token 值。认证时直接按 Token 值查询，命中即视为通过。Token 本身没有独立过期时间，长期有效。

### 3.5 Skip 认证

仅当 `stateful.DefaultConfig.RunTime.SkipTokenValidate == true` 时允许使用。会构造一个伪造的 `Visitor`，其 Scope 为请求中指定的值（如 `System`），便于本地开发和集成测试。

## 4. 授权机制

### 4.1 Feature-Action 权限模型

权限由 **Feature（功能维度）** 和 **Action（操作维度）** 组合描述：

```go
type FeatureAuthorition struct {
    Feature Feature
    Action Action
}
```

`Feature` 为字符串，如 `FeatureAPIKey`、`FeatureRoute`、`FeatureToken` 等。

`Action` 使用位掩码：

```go
const (
    ActionDeny Action = 1 << iota // 000001
    ActionRead // 000010
    ActionReadAll // 000010（与 Read 同值）
    ActionUpdate // 000100
    ActionCreate // 001000
    ActionDelete // 010000
    ActionExport // 100000
)
```

提供 `Grant`、`Revoke`、`IsAllowed` 三个位运算方法。

### 4.2 Endpoint 上的权限声明

每个 `xreq.Endpoint` 通过 `Authorizer` 字段声明所需权限：

```go
var APIKeyCreateRoute = &xreq.Endpoint{
    Path: "/api-keys",
    Method: http.MethodPost,
    Authorizer: iauth.FA(iauth.FeatureAPIKey, iauth.ActionCreate),
}
```

- `FA(Feature, Action)`：仅校验 Feature-Action；
- `FAP(Feature, Action)`：除校验 Feature-Action 外，还校验 Visitor 与当前产品线的绑定关系（`ValidateProduct=true`）。

### 4.3 scope2permission 映射

全局变量 `scope2permission` 定义了每个 Scope 对每个 Feature 拥有哪些 Action：

```go
var scope2permission = map[string]map[Feature]Action{
    ScopeSystem: {
        FeatureAPIKey: actionAll,
        // ... 所有 Feature 均为 actionAll
    },
    ScopeSupport: {
        FeatureAPIKey: ActionExport,
        // ... 仅 Export
    },
}
```

- `ScopeSystem`：所有 Feature 拥有全部 Action；
- `ScopeSupport`：仅部分 Feature 拥有 `ActionExport`，用于只读导出场景。

### 4.4 授权校验流程

`AuthorizeManager.Authorizate` 执行以下步骤：

1. 从 `context` 取出 `Visitor`；
2. 若 `Visitor.IsAdmin()` 为 `true`，直接放行；
3. 遍历 `Visitor.GetScopes()`，在 `scope2permission` 中查找对应 Feature 的 Action 位图；
4. 判断所需 Action 是否被允许；
5. 若 `authrizer.ValidateProduct == true`，再调用 `IsVisitorProductGranted` 校验 Visitor 与当前产品线的绑定关系。

### 4.5 产品线绑定校验

用户 / Token 与产品线的绑定关系存储在 `user_products` 表：

```go
func (m *AuthorizeManager) IsVisitorProductGranted(ctx context.Context, v *Visitor, product *ibasic.Product) (bool, error) {
    if user := v.User; user != nil {
        return m.storager.IsUserProductGranted(ctx, user, product)
    }
    return m.storager.IsTokenProductGranted(ctx, v.Token, product)
}
```

- `ScopeSystem` 管理员直接放行，不校验产品线绑定；
- 已移除 `ScopeProduct`，产品线绑定校验路径保留在代码中但不再被 OpenAPI 使用。

## 5. 中间件集成

### 5.1 全局中间件链

```text
HTTP Request
    │
    ▼
MCRecovery ──► MCLogger ──► MCCors
    │
    ▼
/open-api/v1: McProductProbe ──► McUserProbe
/inner-api/v1: McUserProbe
```

### 5.2 `McUserProbe`

`endpoints/middleware/user_probe.go`：

1. 读取 `Authorization` Header；
2. 按空格切分为 `Type` 和 `Identify`；
3. 调用 `AuthenticateManager.Authenticate`；
4. 将返回的 `Visitor` 写入 `context`。

若 Header 为空，则不做认证（匿名），后续接口若配置 `Authorizer` 会鉴权失败。

### 5.3 `McProductProbe`

`endpoints/middleware/product_probe.go`：

1. 从 URL Path 参数中解析 `product_id` 或 `product_name`；
2. 查询 `products` 表；
3. 将 `Product` 写入 `context`。

仅对 `/open-api/v1` 生效。InnerAPI 不解析产品线上下文。

### 5.4 Endpoint 注册时挂载鉴权

`lib/xreq/result.go` 中 `Endpoint.Register`：

```go
if authorizer := ep.Authorizer; authorizer != nil {
    router = router.NewRoute().Subrouter()
    router.Use(func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(rw http.ResponseWriter, req *http.Request) {
            err := container.AuthorizeManager.Authorizate(req.Context(), authorizer)
            if err != nil {
                ErrorRender(err, rw, req)
                return
            }
            next.ServeHTTP(rw, req)
        })
    })
}
```

每个带 `Authorizer` 的 Endpoint 会单独创建一个 Subrouter，在其上挂载鉴权中间件。

## 6. OpenAPI 认证授权接口

| 接口 | 路径 | 说明 | 是否需要认证 |
|------|------|------|-------------|
| 密码登录 | `POST /auth/session-keys` | 用户名密码登录，返回 Session Key（固定 `is_admin=true`） | 否 |
| 销毁 Session | `DELETE /auth/session-keys/{session_key}` | 登出 | 否 |
| 创建 Token | `POST /auth/tokens` | 创建长期 Token，`scope` 仅支持 `System`/`Support` | 是（`FeatureToken + Create`） |
| 删除 Token | `DELETE /auth/tokens/{token_name}` | 删除 Token | 是 |
| Token 列表 | `GET /auth/tokens` | | 是 |
| Token 详情 | `GET /auth/tokens/{token_name}` | | 是 |
| 创建用户 | `POST /auth/users` | `password` 必填，`is_admin` 仅支持 `true` | 是（`FeatureUser + Create`） |
| 删除用户 | `DELETE /auth/users/{user_name}` | | 是 |
| 用户列表 | `GET /auth/users` | 返回 `user_name`、`is_admin`（固定 `true`） | 是 |
| 用户详情 | `GET /auth/users/{user_name}` | | 是 |
| 设置管理员 | `PATCH /auth/users/{user_name}/is_admin` | 固定为 `true` | 是 |
| 修改密码 | `PATCH /auth/users/{user_name}/passwd` | 同时清空 Session Key | 是 |
| 获取导航配置 | `GET /meta` | | 否 |

## 7. 数据库存储

### 7.1 `users` 表

| 字段 | 说明 |
|------|------|
| `id` | 主键 |
| `name` | 用户名 / Token 名 |
| `type` | `0`=用户，`1`=Token |
| `password` | 用户密码（明文存储） |
| `ticket` | Session Key 或 Token 值 |
| `ticket_created_at` | Session Key 创建时间 |
| `scopes` | 权限作用域，多个用逗号拼接 |

### 7.2 `user_products` 表

| 字段 | 说明 |
|------|------|
| `user_id` | 用户/Token ID |
| `product_id` | 产品线 ID |

联合主键 `(user_id, product_id)`。OpenAPI 不再写入该表，但表结构保留供未来多租户扩展。

## 8. 典型流程示例

### 8.1 Dashboard 登录并调用 OpenAPI

```text
1. POST /auth/session-keys
   Body: {user_name, password}
   Response: {session_key, ...}

2. 后续请求 Header: Authorization: Session <session_key>

3. McUserProbe 解析并认证，Visitor 写入 context

4. 访问 POST /api-keys
   Endpoint.Authorizer = FA(FeatureAPIKey, ActionCreate)
   AuthorizeManager.Authorizate 校验通过
```

### 8.2 Conf Agent 拉取 InnerAPI

```text
1. 使用 Token 调用 GET /inner-api/v1/configs/mod-api-key?version=...

2. Header: Authorization: Token <token_value>

3. McUserProbe 认证该 Token

4. Endpoint.Authorizer = FA(FeatureAPIKey, ActionExport)
   Token Scope 需包含对应 Export 权限
```

## 9. 边界情况与注意事项

| 场景 | 行为 |
|------|------|
| `Authorization` Header 为空 | 匿名请求；若访问需要鉴权的接口则返回授权失败 |
| Session Key 过期 | 返回 `Authenticate Fail：Session Key Expired` |
| Token 不存在 | 返回 `Authenticate Fail：Token Wrong` |
| 密码错误 | 返回 `Authenticate Fail：Password Wrong` |
| 无 Feature 权限 | 返回 `Authorizate Fail：Feature Access Deny`（HTTP 402） |
| 未绑定产品线 | OpenAPI 已移除 Product Scope，该场景不再出现；底层路径保留 |
| `SkipTokenValidate=true` | 任意 `Skip <scope>` 请求头可通过认证，仅用于调试 |
| `ActionRead` 与 `ActionReadAll` 同值 | 代码中两者位掩码相同，权限上等价 |
| 管理员不校验产品线 | `IsAdmin()` 为 `true` 时直接放行，不检查 `user_products` |

---

## 10. 安全建议

1. **密码应加密存储**：当前 `users.password` 为明文，建议改为 bcrypt / scrypt 哈希。
2. **Session Key 建议支持刷新机制**：当前仅通过过期时间控制，建议支持主动刷新和并发登录限制。
3. **Token 建议支持过期与吊销**：当前 Token 长期有效，建议增加过期时间或吊销列表。
4. **敏感接口应使用 HTTPS**：Session Key 和 Token 在 Header 中传输，必须配合 TLS。
