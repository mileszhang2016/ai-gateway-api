# 配额余额同步机制

## 1. 设计背景与目标

在 AI 网关的配额管理体系中，API-Key / Entity 的配额消耗发生在请求链路（由 BFE / 网关代理层实时扣减），而管理面（`ai-gateway-api`）需要持久化记录配额计划的余额，用于：

- OpenAPI 查询接口展示 `used` / `remaining`；
- 后台管理判断配额是否耗尽；
- 周期性（自然周 / 自然月）自动重置配额。

**核心矛盾**：请求链路扣减配额需要高并发、低延迟，因此使用 **Redis** 作为实时计数器；而余额持久化又需要 **关系型数据库** 保证数据可靠性与可查询性。RMB 配额涉及小数，为避免浮点误差，内部采用定点数存储。

**解决思路**：采用 **“Redis 实时计数 + 数据库定时同步”** 的混合架构：

- Redis 存储当前剩余配额（热数据），请求链路直接读写；
- `quota_balances` 表持久化余额（冷数据），由后台定时任务周期性回写；
- 手动重置 / 周期重置时，同步更新 Redis 与数据库，保证两者最终一致；
- RMB 配额内部精度为 8 位小数（1e-8 元），对外统一按 4 位小数展示；Redis Lua 脚本使用整数运算避免浮点误差。

## 3. 核心数据结构

### 3.1 数据库表 `quota_balances`

```sql
CREATE TABLE `quota_balances` (
  `id` bigint(20) NOT NULL AUTO_INCREMENT COMMENT '主键ID',
  `quota_plan_id` bigint(20) NOT NULL COMMENT '配额计划ID',
  `used` decimal(18,8) DEFAULT 0 COMMENT '已使用量',
  `remaining` decimal(18,8) DEFAULT 0 COMMENT '剩余量',
  `last_reset_at` datetime DEFAULT NULL COMMENT '上次重置时间',
  `created_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `updated_at` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_quota_plan_id` (`quota_plan_id`),
  KEY `idx_remaining` (`remaining`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='配额余额表';
```

### 3.2 Redis Key 规则

```go
// stateful/config_redis.go
func AIUsedQuotaKey(key string) string {
    return fmt.Sprintf("QUOTA_%s", key)
}
```

| 对象类型 | Redis Key 示例 | 说明 |
| --- | --- | --- |
| API-Key | `QUOTA_AI_product-abc123...` | 以 API-Key 的实际 `key` 值作为后缀 |
| Entity | `QUOTA_entity-1` | 以 `entity_id` 作为后缀 |
| 值语义 | 当前**剩余配额** | 网关层扣减时递减；`unit=total_token` 时值为整数，`unit=RMB` 时内部以 1e-8 元为单位的定点整数存储 |

> 注：与旧实现不同，当前 Redis Key **不再拼接 `KeyCreateAt` 时间戳**，生命周期与 API-Key / Entity 保持一致，避免 Key 膨胀。
>
> **RMB 配额精度说明**：
> - 内部精度：8 位小数（1e-8 元）定点数；
> - 外部展示：统一按 4 位小数输出；
> - Redis Lua 脚本使用整数运算避免浮点误差，即将 RMB 成本乘以 1e8 后转为整数进行扣减；
> - `unit = "total_token"` 仍直接使用整数计数；
> - `unit = "RMB"` 时，请求链路在扣减前需将实际成本转换为内部定点整数。

## 4. 同步管理器（BalanceSyncManager）

### 4.1 文件位置

- `model/quota/balance_sync.go`
- `model/quota/scheduler.go`

### 4.2 组件定义

```go
type BalanceSyncManager struct {
    txn itxn.TxnStorager
    apiKeyStorager icluster_conf.APIKeyStorager
    balanceStorager QuotaBalanceStorager
    planStorager QuotaPlanStorager
    entityStorager EntityStorager
    quotaCache quotacache.QuotaCache  // 新增：实时配额缓存抽象
}
```

### 4.3 同步所有配额余额 `SyncAllBalances`

调度器每次触发时，先执行余额同步：

1. 查询所有 **非无限配额** 的 `quota_plan`；
2. 对每个计划，找出所有关联的 API-Key 与 Entity；
3. 从 Redis 读取每个对象的**剩余量**并累加，得到 `totalRemaining`；
   - `unit = "RMB"` 时，Redis 中存储的是以 1e-8 元为单位的定点整数，落库前转换为 `DECIMAL(18,8)`；
4. 由 `plan.Quota - totalRemaining` 计算 `totalUsed`（最小为 0）；
5. 更新 `quota_balances` 表的 `used` 与 `remaining`。

```go
func (m *BalanceSyncManager) SyncAllBalances(ctx context.Context) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        plans, err := m.planStorager.FetchQuotaPlanList(ctx, &QuotaPlanFilter{
            Unlimited: lib.PBool(false),
        })
        if err != nil {
            return err
        }

        for _, plan := range plans {
            if err := m.syncPlanBalance(ctx, plan); err != nil {
                fmt.Printf("Failed to sync balance for plan %d: %v\n", *plan.ID, err)
            }
        }
        return nil
    })
}
```

### 4.4 单个计划同步 `syncPlanBalance`

```go
func (m *BalanceSyncManager) syncPlanBalance(ctx context.Context, plan *QuotaPlanParam) error {
    // 1. 读取关联 API-Key
    apiKeys, err := m.apiKeyStorager.FetchAPIKeyList(ctx, &icluster_conf.APIKeyFilter{
        QuotaPlanID: plan.ID,
    })
    // ...

    // 2. 读取关联 Entity
    var entities []*EntityParam
    if m.entityStorager != nil {
        entities, err = m.entityStorager.FetchEntityList(ctx, &EntityFilter{
            QuotaPlanID: plan.ID,
        })
        // ...
    }

    // 3. 累加 Redis 剩余量
    var totalRemaining int64
    for _, apiKey := range apiKeys {
        if apiKey.Key == nil || apiKey.KeyCreateAt == nil {
            continue
        }
        remaining, err := m.quotaCache.GetRemaining(ctx, *apiKey.Key, plan.Unit)
        if err != nil {
            continue
        }
        totalRemaining += quota.PtrToRedisValue(&remaining, plan.Unit)
    }
    for _, entity := range entities {
        if entity.EntityID == nil {
            continue
        }
        remaining, err := m.quotaCache.GetRemaining(ctx, *entity.EntityID, plan.Unit)
        if err != nil {
            continue
        }
        totalRemaining += quota.PtrToRedisValue(&remaining, plan.Unit)
    }

    // 4. 反推已用量并落库
    totalUsed := *plan.Quota - totalRemaining
    if totalUsed < 0 {
        totalUsed = 0
    }
    _, err = m.balanceStorager.UpdateQuotaBalance(ctx, &QuotaBalanceFilter{
        QuotaPlanID: plan.ID,
    }, &QuotaBalanceParam{
        Used: lib.PInt64(totalUsed),
        Remaining: lib.PInt64(totalRemaining),
    })
    return err
}
```

**关键设计点**：

- Redis 中存储的是**剩余量**，数据库中同时记录 `used` 与 `remaining`，便于查询与监控；
- `unit = "RMB"` 时，Redis 使用定点整数存储（1e-8 元），数据库 `quota_balances` 使用 `DECIMAL(18,8)`，API 层对外统一按 4 位小数展示；
- 若 Redis 读取失败（如 Key 不存在），则跳过该对象，不纳入本次累加；
- 同步过程中单条失败不影响其他计划。

## 5. 调度器（QuotaResetScheduler）

### 5.1 调度策略

当前实现采用**单一高频调度器**，每分钟执行一次：

```go
func (s *QuotaResetScheduler) run() {
    s.resetQuotasWithRecover()

    ticker := time.NewTicker(1 * time.Minute)
    defer ticker.Stop()

    for {
        select {
        case <-ticker.C:
            s.resetQuotasWithRecover()
        case <-s.stopCh:
            return
        }
    }
}
```

每次调度串行执行两步：

1. `SyncAllBalances()`：将 Redis 中的剩余量回写到数据库；
2. `ResetExpiredBalances()`：检查并执行到期配额重置。

```go
func (s *QuotaResetScheduler) resetQuotas() {
    ctx := context.Background()
    now := time.Now()

    stateful.AccessLogger.Info("Starting quota scheduler tasks at %v", now)

    if err := s.balanceSyncMgr.SyncAllBalances(ctx); err != nil {
        stateful.AccessLogger.Error("Failed to sync all balances: %v", err)
    }

    if err := s.balanceSyncMgr.ResetExpiredBalances(ctx); err != nil {
        stateful.AccessLogger.Error("Failed to reset expired balances: %v", err)
    }
}
```

### 5.2 启动注册

## 6. 配额重置机制

### 6.1 周期重置 `ResetExpiredBalances`

支持两种重置周期：

- `weekly`：自然周，每周一 00:00:00 重置；
- `monthly`：自然月，每月 1 日 00:00:00 重置。

判断逻辑：

```go
func (m *BalanceSyncManager) shouldResetByPeriod(
    lastResetAt *time.Time,
    resetPeriod string,
    now time.Time,
) bool {
    if lastResetAt == nil {
        return true
    }

    switch resetPeriod {
    case "weekly":
        return getWeekStart(now).After(getWeekStart(*lastResetAt))
    case "monthly":
        return getMonthStart(now).After(getMonthStart(*lastResetAt))
    }
    return false
}
```

`getWeekStart` / `getMonthStart` 将时间归一化为周一或每月 1 日的 00:00:00（本地时区）。

### 6.2 重置执行流程

1. 查询 `reset_period` 为 `weekly` 或 `monthly` 且非无限配额的计划；
2. 判断是否需要重置；
3. 对计划下所有 API-Key / Entity 的 Redis Key 执行 `IncrBy(delta)`，将剩余量调整为配额总量；
4. 更新 `quota_balances`：
   - `used = 0`
   - `remaining = plan.Quota`
   - `last_reset_at = now()`
   - `unit = "RMB"` 时，`remaining` 仍按 `DECIMAL(18,8)` 写入，Redis 中按 1e-8 元定点整数设置。

```go
func (m *BalanceSyncManager) ResetExpiredBalances(ctx context.Context) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        plans, err := m.planStorager.FetchQuotaPlanList(ctx, &QuotaPlanFilter{
            ResetPeriod: []string{"weekly", "monthly"},
            Unlimited: lib.PBool(false),
        })
        // ...

        now := time.Now()
        for _, plan := range plans {
            balance, err := m.balanceStorager.FetchQuotaBalance(ctx, &QuotaBalanceFilter{
                QuotaPlanID: plan.ID,
            })
            // ...

            if m.shouldResetByPeriod(balance.LastResetAt, *plan.ResetPeriod, now) {
                if err := m.resetAPIKeysRedisUsage(ctx, *plan.ID); err != nil {
                    continue
                }
                _, _ = m.balanceStorager.UpdateQuotaBalance(ctx, &QuotaBalanceFilter{
                    QuotaPlanID: plan.ID,
                }, &QuotaBalanceParam{
                    Used: lib.PInt64(0),
                    Remaining: plan.Quota,
                    LastResetAt: lib.PTime(now),
                })
            }
        }
        return nil
    })
}
```

### 6.3 Redis 归零策略

无论是周期重置还是手动重置，均使用 **原子 `IncrBy(delta)`** 而非 `SET 0`：

```go
if err := quotaCache.ResetToQuota(ctx, key, quotaTotalPtr, unit); err != nil {
    // 记录日志，继续处理下一个对象
}
```

**原因**：

- 并发场景下，`SET` 会覆盖其他请求刚刚扣减的计数，导致配额透支；
- `IncrBy(delta)` 基于当前值做增量调整，可与其他扣减操作串行化；
- Key 不存在时直接 `IncrBy(quotaTotal)` 完成初始化。

### 6.4 手动重置接口

提供两个 OpenAPI 端点，均调用 `QuotaPlanManager.ResetBalance(..., updateLastResetAt=false)`：

- `POST /api-keys/{id}/quota-plan/reset`
- `POST /entities/{id}/quota-plan/reset`

`updateLastResetAt=false` 的设计意图：手动重置不应干扰周期调度器对自然周 / 自然月的判断。

`QuotaPlanManager.ResetBalance` 核心逻辑：

```go
func (m *QuotaPlanManager) ResetBalance(
    ctx context.Context,
    planID int64,
    newQuota *float64,
    updateLastResetAt bool,
) error {
    return m.txn.AtomExecute(ctx, func(ctx context.Context) error {
        // 1. 校验 plan 存在且非无限
        // 2. 若 newQuota 不为空，更新 plan.quota
        // 3. 重置 balance 的 used / remaining，并按需更新 last_reset_at
    })
}
```

## 7. Redis Key 生命周期

| 阶段 | 行为 | 说明 |
| --- | --- | --- |
| **API-Key / Entity 创建** | 若配额有限，调用 `quotacache.SetRemaining` 将 Redis 值设为 `quota` | 由 `model/icluster_conf.APIKeyManager.CreateAPIKey` / `model/quota.EntityManager.CreateEntity` 在事务提交后调用；`unit=RMB` 时 Redis 存定点整数 |
| **Entity 无限配额** | 设置默认大值 `100000000` | 保证无限配额对象在 Redis 中也有可读取的剩余量 |
| **请求链路消耗** | 网关层对 `QUOTA_<key>` 做递减 | 不在 `ai-gateway-api` 内实现；`unit=RMB` 时 Lua 使用整数运算 |
| **手动重置** | `IncrBy(delta)` 调整为新的 `quota` | 不删除/新建 Key；`unit=RMB` 时按定点整数计算 delta |
| **周期重置** | `IncrBy(delta)` 调整为 `plan.Quota` | 同时更新 `last_reset_at`；`unit=RMB` 时按定点整数计算 delta |
| **同步任务** | 读取 Redis 值，回写 `quota_balances` | 不修改 Redis；`unit=RMB` 时定点整数转 `DECIMAL(18,8)` |

### 8.3 实时剩余量查询 `GetRemainingQuota`

`model/icluster_conf/api_key.go` 提供了实时读取 Redis 的辅助函数，供网关层或内部逻辑使用：

```go
func GetRemainingQuota(ctx context.Context, param *APIKeyParam) (*float64, error) {
    if param.UnlimitedQuota != nil && *param.UnlimitedQuota {
        return nil, nil
    }

    // 关联的 quota plan 为无限配额时，同样返回 nil
    if param.QuotaPlan != nil && param.QuotaPlan.Unlimited != nil && *param.QuotaPlan.Unlimited {
        return nil, nil
    }

    if param.QuotaPlan == nil || param.QuotaPlan.Quota == nil {
        return nil, nil
    }
    if quotaCache == nil {
        return param.QuotaPlan.Quota, nil
    }

    remain, err := quotaCache.GetRemaining(ctx, *param.Key, param.QuotaPlan.Unit)
    if err != nil {
        return nil, err
    }
    if remain < 0 {
        remain = 0
    }
    return &remain, nil
}
```

**语义**：

- API-Key 自身或关联 quota plan 为无限配额：返回 `nil`，表示无限制；
- 有限配额且 Redis Key 不存在：返回 `plan.Quota`（未使用）；
- 有限配额且 Redis Key 存在：返回 Redis 当前值；`unit=RMB` 时 Redis 值为定点整数，需除以 1e8 转换为浮点数；
- 值为负时截断为 0。

## 9. 创建与删除时的一致性处理

### 9.1 创建时初始化

- API-Key / Entity 创建若携带**有限配额计划**，`model/icluster_conf.APIKeyManager.CreateAPIKey` / `model/quota.EntityManager.CreateEntity` 会在事务提交后通过 `quotacache.QuotaCache.SetRemaining` 向 Redis 写入初始剩余量；
- 数据库 `quota_balances` 记录由 Manager 在事务内创建；
- 若 Redis 写入失败，接口可能返回错误，但数据库记录已存在；后续同步任务会根据 Redis 实际值修正数据库。

### 9.2 更新配额计划时的 Redis 处理

无论是 `PUT` 全量更新还是 `PATCH` 部分更新，只要请求体中包含 `quota_plan` 且 `unlimited != true`，Manager 层（`APIKeyManager.UpdateAPIKey` / `EntityManager.UpdateEntity`）会完成数据库更新，并在事务提交后通过 `quotacache.QuotaCache` 执行一致性动作：

1. 从更新前的对象中读取旧 `quota`（`oldQuota`）；
2. 完成数据库内 `api_keys` / `entities` 及 `quota_balances` 的更新；
3. 若 `quota_balances` 记录不存在，则创建；
4. 通过 `QuotaCache` 调整 Redis 剩余量：
   - Key 不存在：调用 `SetRemaining` 初始化为 `newQuota`；
   - Key 存在：读取当前剩余量并计算 `delta = newQuota - oldRemaining`，调用 `SetRemaining` 或基于 `IncrBy(delta)` 的原子调整。

示例逻辑（以 API-Key 更新为例，已下沉到 `model/icluster_conf`）：

```go
if param.QuotaPlan != nil && (param.QuotaPlan.Unlimited == nil || !*param.QuotaPlan.Unlimited) &&
    updated != nil && updated.QuotaPlanID != nil {

    balance, err := container.QuotaPlanManager.FetchQuotaBalance(ctx, *updated.QuotaPlanID)
    if balance == nil {
        container.QuotaPlanManager.CreateQuotaBalance(ctx, *updated.QuotaPlanID, param.QuotaPlan.Quota)
    }

    if err := rppm.quotaCache.SetRemaining(ctx, *updated.Key, param.QuotaPlan.Quota, param.QuotaPlan.Unit); err != nil {
        // 记录日志，继续返回更新结果
    }
}
```

> 注：端点层不再直接调用 Redis Client，统一通过 `model/icluster_conf.APIKeyManager` / `model/quota.EntityManager` 内注入的 `quotacache.QuotaCache` 完成缓存一致性动作。

**注意**：

- 如果新配额 **小于** 旧配额，`delta` 为负，Redis 剩余量会相应减少；
- 如果新配额 **大于** 旧配额，`delta` 为正，Redis 剩余量会相应增加；
- 该操作基于 `IncrBy`，在并发请求消费配额时仍可保证原子性。

### 9.3 删除时清理

- `APIKeyManager.DeleteAPIKey` / `EntityManager.DeleteEntity` 在事务内级联删除 `quota_balance`、`quota_plan` 等关联记录；
- 当前实现**不主动删除 Redis Key**，由 Redis 自身的过期策略或后续 Key 复用处理。

## 10. 边界情况与注意事项

| 场景 | 当前行为 | 说明 |
| --- | --- | --- |
| Redis Key 不存在 | 同步时跳过；查询实时配额时返回 `plan.Quota` | `GetRemainingQuota` 中已做 `redigo: nil returned` 兼容；`unit=RMB` 时同样按定点整数处理 |
| Redis 值为负 | 同步时 `totalUsed` 置 0；查询时 `remain` 置 0 | 防止透支导致数据库显示异常 |
| RMB 配额小数位超过 8 位 | 接口层校验拒绝或截断 | 内部定点精度为 1e-8 元；对外统一按 4 位小数展示 |
| 配额计划无 balance 记录 | 周期/手动重置时会新建 | `ResetBalance` 中 balance 为空则创建 |
| 无限配额计划 | 不参与同步与重置 | `Unlimited=true` 时无 `quota_balances` 记录 |
| 多实例部署 | 各实例均会启动调度器 | 当前未加分布式锁，存在重复同步风险；建议后续优化 |
| 时区 | 使用服务器本地时区 | `getWeekStart` / `getMonthStart` 依赖 `time.Now()` 的本地时区 |
| 单条失败 | 记录日志并继续 | 不影响其他计划 / 对象的处理 |

## 11. 性能优化建议

1. **Redis Pipeline**：`syncPlanBalance` 中对同一计划下多个 API-Key / Entity 的读取可合并为一次 Pipeline，减少 RTT。
2. **批量更新数据库**：当前为每个计划单独更新一次 `quota_balances`，可改为按批次 `UPDATE`。
3. **增量同步**：记录每个计划的上次同步时间或 Redis 版本号，仅同步发生变化的对象。
4. **分布式锁**：多实例部署时，使用 Redis 分布式锁（如 `SETNX`）确保只有一个实例执行同步与重置任务。
5. **失败重试**：对同步失败的计划加入重试队列，避免等到下一调度周期才修正。

## 12. 监控与告警建议

| 指标 | 类型 | 用途 |
| --- | --- | --- |
| `quota_sync_total` / `quota_sync_failed` | Counter | 同步任务成功 / 失败次数 |
| `quota_sync_duration_seconds` | Histogram | 单次同步耗时 |
| `quota_usage_ratio` | Gauge | `used / quota`，按 plan 聚合 |
| `quota_near_exhaustion_keys` | Gauge | 使用率 > 90% 的 API-Key / Entity 数量 |
| `quota_reset_total` / `quota_reset_failed` | Counter | 周期重置成功 / 失败次数 |

建议对以下情况触发告警：

- 连续多次同步任务失败；
- 大量 API-Key 配额使用率超过阈值；
- 周期重置任务连续失败导致余额未按时重置。
